# คู่มือฟีเจอร์สร้างรายการรายจ่ายอัตโนมัติและ Checklist ก่อนเผยแพร่ Google Play

## ส่วนที่ 1: คู่มือผู้ใช้ฟีเจอร์ “ทุกเดือน”

### ฟีเจอร์นี้ทำอะไร

ฟีเจอร์ **ทุกเดือน** ใช้สำหรับรายจ่ายที่เกิดซ้ำเป็นประจำ เช่น ค่าอินเทอร์เน็ต ค่าโทรศัพท์ ค่าเช่าบ้าน ค่าสมาชิก หรือค่าสาธารณูปโภค

เมื่อผู้ใช้เปิดหน้า Home ระบบจะตรวจสอบรายการที่ตั้งเป็น “ทุกเดือน” และสร้างรายการของเดือนถัดไปให้อัตโนมัติ โดยคัดลอกข้อมูลสำคัญจากรายการเดิม เช่น ชื่อรายการ ผู้รับเงิน จำนวนเงิน หมวดหมู่ เลขอ้างอิง และหมายเหตุ

ระบบจะสร้างรายการแต่ละรอบเพียงครั้งเดียว แม้เปิดแอปซ้ำหรือมีการตรวจสอบพร้อมกัน จึงช่วยลดโอกาสเกิดรายการซ้ำ

### วิธีตั้งรายการให้สร้างอัตโนมัติ

1. เปิดแอป **บ้านเรา** และไปที่หน้า **Home**
2. กดปุ่ม **เพิ่มรายจ่าย**
3. กรอกข้อมูลที่จำเป็น ได้แก่ ชื่อรายการและจำนวนเงิน
4. เลือกหมวดหมู่ตามต้องการ
5. ตรวจสอบช่อง **วันครบรอบกำหนดชำระ** แล้วเลือกวันที่ที่ต้องการ หากวันที่ถูกกรอกไว้แล้วสามารถแก้ไขได้
6. ที่ตัวเลือกการทำซ้ำ ให้เลือก **ทุกเดือน**
7. ตรวจสอบข้อมูลทั้งหมด โดยเฉพาะจำนวนเงินและวันกำหนดชำระ
8. กด **บันทึก**

หลังจากบันทึก รายการจะมีสถานะหรือป้ายกำกับว่า **ทุกเดือน** ในรายการรายจ่าย

### ระบบสร้างรายการเดือนไหน

ระบบจะตรวจสอบทั้งเดือนปัจจุบันและเดือนถัดไปเมื่อเปิดหน้า Home โดยใช้รายการ “ทุกเดือน” ที่มีอยู่ในเดือนก่อนหน้าเป็นต้นแบบ

ตัวอย่าง:

- บันทึกค่าอินเทอร์เน็ตของเดือนตุลาคมเป็น “ทุกเดือน”
- เมื่อเปิดแอปในช่วงเดือนพฤศจิกายน ระบบจะสร้างรายการของเดือนพฤศจิกายนจากรายการเดือนตุลาคม
- ระบบจะเตรียมตรวจสอบเดือนถัดไปด้วย เพื่อให้รายการต่อเนื่องเมื่อผู้ใช้เปลี่ยนช่วงเดือน

หากตั้งวันชำระเป็นวันที่ 31 แต่เดือนเป้าหมายมีเพียง 28, 29 หรือ 30 วัน ระบบจะปรับเป็นวันสุดท้ายของเดือนนั้นโดยอัตโนมัติ

### ข้อมูลใดที่ระบบคัดลอกไปเดือนถัดไป

ระบบจะคัดลอกข้อมูลต่อไปนี้จากรายการต้นแบบ:

- ชื่อรายการ
- ผู้รับเงิน
- จำนวนเงิน
- หมวดหมู่
- วันครบรอบกำหนดชำระ โดยปรับปีและเดือนเป็นเดือนเป้าหมาย
- เลขอ้างอิง
- หมายเหตุ
- สถานะการทำซ้ำเป็น “ทุกเดือน”

ไฟล์บิลจะ **ไม่ถูกคัดลอกไปยังรายการใหม่** ผู้ใช้สามารถแนบบิลของเดือนใหม่แยกต่างหากได้

### ถ้าต้องการหยุดการสร้างอัตโนมัติ

1. เปิดรายการรายจ่ายที่มีป้าย **ทุกเดือน**
2. กดแก้ไขรายการ
3. เปลี่ยนตัวเลือกการทำซ้ำจาก **ทุกเดือน** เป็น **ไม่ทำซ้ำ**
4. กดบันทึก

ตั้งแต่รอบถัดไป ระบบจะไม่สร้างรายการต่อจากรายการนั้น

### ถ้าจำนวนเงินหรือวันกำหนดชำระเปลี่ยน

ให้แก้ไขรายการต้นแบบหรือรายการล่าสุด แล้วตรวจสอบว่าเลือก **ทุกเดือน** อยู่ หากต้องการให้เดือนต่อไปใช้จำนวนเงินหรือวันใหม่ ควรแก้ไขรายการของเดือนล่าสุดก่อนที่ระบบจะสร้างรอบถัดไป

### ถ้าต้องการลบรายการที่ระบบสร้าง

ผู้ใช้สามารถแก้ไขหรือลบรายการได้ตามปกติ แต่ถ้ารายการต้นแบบของเดือนก่อนหน้ายังตั้งเป็น **ทุกเดือน** อยู่ ระบบอาจสร้างรายการของเดือนเป้าหมายกลับมาอีกเมื่อมีการตรวจสอบรอบถัดไป ดังนั้นหากต้องการหยุดรายการถาวร ให้ปิดการทำซ้ำที่รายการต้นแบบด้วย

### กรณีออฟไลน์

หากบันทึกรายการขณะไม่มีอินเทอร์เน็ต แอปจะเก็บรายการไว้ในคิวออฟไลน์ และพยายามส่งข้อมูลเมื่อกลับมาออนไลน์ ควรเปิดแอปหลังเชื่อมต่ออินเทอร์เน็ตเพื่อให้คิวถูกประมวลผลและให้ระบบตรวจสอบรายการรายเดือนล่าสุด

### วิธีตรวจสอบว่าทำงานสำเร็จ

- เปิดหน้า Home แล้วเลือกเดือนเป้าหมาย
- ตรวจดูว่ารายการปรากฏในเดือนนั้น
- ตรวจสอบป้าย **ทุกเดือน**
- ตรวจสอบจำนวนเงิน หมวดหมู่ และวันครบรอบกำหนดชำระ
- หากรายการไม่ปรากฏ ให้ตรวจว่าเดือนก่อนหน้ามีรายการต้นแบบที่ยังตั้งเป็น “ทุกเดือน” หรือไม่ และตรวจสถานะอินเทอร์เน็ต

## ส่วนที่ 2: Checklist ก่อนเผยแพร่แอปบน Google Play Console

ใช้ Checklist นี้ก่อนกด **Start rollout** หรือ **Send for review** ทุกครั้ง

### A. ตรวจ build และไฟล์ Android

- [ ] ใช้ไฟล์ **Android App Bundle (.aab)** สำหรับ production release
- [ ] ตรวจ `versionName` ให้ตรงกับรุ่นที่จะประกาศ เช่น `1.0.12`
- [ ] เพิ่ม `versionCode` จากรุ่นก่อนหน้าแล้ว เช่นรุ่นนี้ใช้ `13`
- [ ] ตรวจว่า application ID/package name ถูกต้อง: `space.manus.homeexpapp`
- [ ] ตรวจว่า AAB สร้างจาก source ล่าสุด ไม่ใช่ไฟล์ build เก่า
- [ ] ตรวจว่า release เป็น **signed release** ไม่ใช่ debug build
- [ ] ตรวจ app signing และ upload key ใน Play Console ให้ถูกต้อง
- [ ] เก็บ keystore และรหัสผ่านไว้นอก repository และมีสำรองที่ปลอดภัย
- [ ] ตรวจว่า target API เป็นไปตามข้อกำหนดปัจจุบันของ Google Play สำหรับวันที่ส่งจริง ปัจจุบัน Google ระบุว่าเริ่ม 31 สิงหาคม 2026 แอปใหม่และแอปอัปเดตต้อง target Android 16 (API 36) ขึ้นไป [1]
- [ ] เปิด AAB ใน Play Console และตรวจ APK generated จาก App Bundle ว่าติดตั้งได้
- [ ] ตรวจ checksum ของไฟล์ release และบันทึกไว้ในประวัติการปล่อย

### B. ทดสอบฟีเจอร์หลักของแอป

- [ ] เพิ่มรายจ่ายแบบไม่ทำซ้ำได้
- [ ] เพิ่มรายจ่ายแบบ **ทุกเดือน** ได้
- [ ] เปิดแอปซ้ำแล้วไม่เกิดรายการรายเดือนซ้ำ
- [ ] ตรวจกรณีวันที่ 28, 29, 30 และ 31 ของเดือน
- [ ] ตรวจการเปลี่ยนเดือนธันวาคมไปมกราคม
- [ ] แก้ไขและลบรายการได้
- [ ] เปลี่ยนจาก “ทุกเดือน” เป็น “ไม่ทำซ้ำ” แล้วไม่มีรายการรอบใหม่เพิ่ม
- [ ] จำนวนเงิน หมวดหมู่ ผู้รับเงิน เลขอ้างอิง และหมายเหตุถูกคัดลอกถูกต้อง
- [ ] รายการเดือนใหม่ไม่มีไฟล์บิลของเดือนเก่าติดไปโดยไม่ตั้งใจ
- [ ] อัปโหลด JPG/PNG และ PDF ได้
- [ ] ทดสอบบิลภาพใหญ่: เห็นเปอร์เซ็นต์อัปโหลดจริง และกดยกเลิกได้
- [ ] ตรวจว่าการบีบอัดรูปไม่ทำให้ข้อความบนบิลอ่านไม่ได้
- [ ] ทดสอบ OCR กับบิลหลายรูปแบบ รวมถึงบิลที่มีภาษาไทยและตัวเลขไทย
- [ ] ทดสอบ QR Code และ Barcode แล้วตรวจข้อมูลที่เติมในเลขอ้างอิงหรือหมายเหตุ
- [ ] ทดสอบการบันทึกขณะออฟไลน์ และการส่งคิวเมื่อกลับมาออนไลน์
- [ ] ตรวจ export สรุปรายจ่ายเป็น JPG และตรวจชื่อไฟล์กับยอดรวม

### C. ทดสอบหน้าจอและอุปกรณ์

- [ ] ทดสอบอย่างน้อยที่ 320×720, 360×800, 412×915 และ 480×960
- [ ] ทดสอบ Android navigation bar แบบ gesture และแบบ 3-button navigation
- [ ] ตรวจว่า bottom sheet ไม่ทับปุ่ม Home หรือแถบนำทาง
- [ ] ปัดลงเพื่อปิด bottom sheet ได้
- [ ] ช่องที่กรอกผิดมี autofocus และเลื่อนไปยังตำแหน่งที่ผิด
- [ ] ปุ่มบันทึก ปุ่มยกเลิก และปุ่มอัปโหลดกดได้ง่ายบนจอเล็ก
- [ ] ทดสอบ portrait และ landscape หากประกาศรองรับแท็บเล็ต
- [ ] ตรวจ dark mode/light mode หากแอปรองรับ
- [ ] ตรวจขนาดตัวอักษรใหญ่และการตั้งค่าการช่วยเหลือพิเศษ
- [ ] ตรวจการหมุนจอและการกลับเข้าแอปจาก background

### D. ตรวจ Google Play App content

Google Play ให้กรอกข้อมูลในหน้า **App content** เพื่อประเมินความปลอดภัย การปฏิบัติตามนโยบาย และข้อกำหนดทางกฎหมาย [2]

- [ ] เพิ่ม Privacy Policy URL ที่เปิดได้จริงและอธิบายการเก็บ ใช้ และแชร์ข้อมูลของแอป
- [ ] ใส่ Privacy Policy ไว้ในแอปด้วย หากแอปใช้ข้อมูลหรือ permission ที่อยู่ในขอบเขตที่ Google กำหนด [2]
- [ ] ตอบคำถาม Data safety ให้ตรงกับพฤติกรรมจริงของแอป เช่น บัญชีผู้ใช้ ข้อมูลรายจ่าย ไฟล์บิล และข้อมูลที่ส่งไปประมวลผล
- [ ] ตรวจว่าไม่มีข้อมูลบัตรประชาชน รหัสผ่าน หรือข้อมูลลับถูกใส่ในภาพหน้าจอ ตัวอย่างบิล หรือ demo account
- [ ] ประกาศเรื่องโฆษณาให้ถูกต้อง หากไม่มีโฆษณาให้เลือกไม่มีโฆษณา [2]
- [ ] กรอก Target audience and content ให้ตรงกับผู้ใช้จริง
- [ ] ทำ Content rating questionnaire ให้เสร็จ เพื่อไม่ให้แอปถูกจัดเป็น Unrated [2]
- [ ] ตรวจ Permissions declaration หาก release ขอ permission ที่มีความเสี่ยงสูงหรือเป็นข้อมูลอ่อนไหว
- [ ] กรอก App access/sign-in details หากผู้ตรวจต้องล็อกอินเพื่อเข้าถึงฟีเจอร์
- [ ] ระบุวิธีทดสอบฟีเจอร์อัปโหลดบิล, OCR, QR/Barcode และ recurring expenses ในคำแนะนำผู้ตรวจ หากระบบมีส่วนที่เข้าถึงได้เฉพาะหลังล็อกอิน
- [ ] ตรวจ Data deletion/account deletion flow ตามข้อมูลและบัญชีที่แอปเก็บจริง

### E. ตรวจ Store listing

- [ ] ชื่อแอปใน Store listing ตรงกับชื่อในแอป: **บ้านเรา**
- [ ] Short description ไม่กล่าวอ้างเกินจริง และอธิบายประโยชน์หลักชัดเจน
- [ ] Full description ระบุฟีเจอร์บันทึกรายจ่าย รายการทุกเดือน อัปโหลดบิล และสรุปยอดอย่างตรงไปตรงมา
- [ ] Release notes ระบุเฉพาะสิ่งที่มีอยู่จริงในรุ่นนี้
- [ ] ไอคอนแอปมีขนาดและรูปแบบตามข้อกำหนด Google Play
- [ ] Screenshots เป็นภาพจากรุ่นที่จะเผยแพร่จริง และไม่มีข้อมูลส่วนตัวจริง
- [ ] ภาพหน้าจออ่านได้ทั้งบนมือถือขนาดเล็กและหน้า Store listing
- [ ] ข้อมูลผู้พัฒนา อีเมล เว็บไซต์ และช่องทางติดต่อใช้งานได้
- [ ] ตรวจหมวดหมู่และแท็กของแอปให้ตรงกับแอปจัดการรายจ่ายในครัวเรือน
- [ ] ตรวจประเทศ/ภูมิภาคและราคาให้ถูกต้อง

### F. ทดสอบผ่าน Play Console ก่อน production

- [ ] อัปโหลด AAB ไปที่ Internal testing ก่อน
- [ ] ติดตั้งจาก Google Play ไม่ใช่ติดตั้ง APK ด้วยตนเองเท่านั้น
- [ ] ตรวจการอัปเดตจากรุ่นก่อนหน้าโดยไม่ถอนการติดตั้ง
- [ ] ตรวจว่าข้อมูลรายจ่ายเดิมยังอยู่หลังอัปเดต
- [ ] ตรวจ Android App Bundle Explorer และอุปกรณ์ที่รองรับ
- [ ] ตรวจ Pre-launch report และแก้ crash, ANR, permission หรือ compatibility issue
- [ ] ตรวจ Android vitals หลังทดสอบ
- [ ] ให้ผู้ทดสอบลองงานจริงตั้งแต่เพิ่มรายการจนถึงอัปโหลดบิลและดูสรุป
- [ ] เก็บ feedback และแก้ปัญหาที่กระทบการใช้งานก่อน production

หากเป็น **บัญชีนักพัฒนาส่วนบุคคลที่สร้างหลังวันที่ 13 พฤศจิกายน 2023** Google Play กำหนดให้ทำ closed test โดยมีผู้ทดสอบอย่างน้อย 12 คนที่ opt-in ต่อเนื่องอย่างน้อย 14 วัน ก่อนขอ production access [4]

- [ ] ตรวจ Errors summary ต้องไม่มี error ที่บล็อกการเผยแพร่
- [ ] ตรวจ warnings และแก้ไขเท่าที่ทำได้ก่อนส่งตรวจ
- [ ] ตรวจ Publishing overview ว่าไม่มีการเปลี่ยนแปลงอื่นค้างอยู่
- [ ] บันทึก release เป็น draft และตรวจ Preview and confirm อีกครั้ง
- [ ] กดส่งตรวจเมื่อข้อมูลทั้งหมดถูกต้อง
- [ ] หลังอนุมัติ ตรวจหน้าร้านจริงจากอุปกรณ์ Android อย่างน้อยหนึ่งเครื่อง
- [ ] ตรวจ install, update, เปิดแอป, เพิ่มรายจ่าย และ recurring expenses หลังเผยแพร่จริง

Google ระบุว่าขั้นตอน release ประกอบด้วยการสร้าง release, เตรียม AAB และ release notes, ตรวจข้อผิดพลาด จากนั้นจึง rollout ไปยัง track ที่เลือก [3]
